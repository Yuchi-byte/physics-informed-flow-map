# Full-OpenFWI Priors + Inversion Benchmark — Design

**Status: DRAFT for discussion — not yet approved for implementation.**

**Goal:** Train the three prior families (`0001` flow matching, `0002` flow map, `0003` diffusion)
to the best achievable standard on the full 2D OpenFWI collection (all 10 families, ~470k velocity
maps), publish the checkpoints as wandb artifacts, then distill a small, curated, self-contained
**inversion benchmark set** so the bulk dataset can be deleted and all subsequent work (0004
inversion experiments) runs from checkpoints + the benchmark alone.

**Non-goals:** Kimberlina (3D + 2D CO₂) — different grid geometry, incompatible with the
70×70 bridge (`inversion/bridge.py`); conditional priors p(v|d); multi-GPU DDP (single-GPU
runs are fast enough, see §6); changes to reference packages.

---

## 1. Dataset selection

All **10 2D families** from `ashynf/OpenFWI` (HuggingFace). Verified layout + counts (2026-07-06):

| Family | Maps | Layout on HF | Velocity files | Character |
|---|---|---|---|---|
| FlatVel_A/B | 30k each | `data/dataN.npy` + `model/modelN.npy` | already local | flat layers, A clean / B random |
| CurveVel_A/B | 30k each | same | already local | curved/folded layers |
| FlatFault_A/B | 54k each | flat `seis*_*_*.npy` + `vel*_*_*.npy` | ~4.2 GB for 4 fault fams | flat layers + faulting |
| CurveFault_A/B | 54k each | same flat layout | (included above) | curved layers + faulting — hardest structural |
| Style_A/B | 67k each | `data/` + `model/` | ~2.6 GB both | natural-image style transfer — most field-like textures |

Total: **470k maps** (matches the assumption already baked into the three `openfwi_full.yaml`
configs). Complexity coverage: parametric layers → folds → faults → naturalistic textures, which
is exactly the axis on which MFM-G is hypothesised to beat simpler steering.

**Key storage insight — we only need velocity maps.** The priors are unconditional over velocity
maps, and inversion observations are generated by our own Deepwave forward operator
(`physics/forward.py`); the OpenFWI seismic files (`dataN.npy` / `seis*.npy`, 700 MB each, ~98% of
the bytes) are never read. Downloading only `model/*.npy` + `vel*.npy` gets the six missing
families in **~7 GB**, not ~500 GB:

```bash
uv run hf download ashynf/OpenFWI --repo-type dataset \
  --include "*model*.npy" "*vel*.npy" \
  --local-dir /workspace/physics-informed-flow-map/data/openfwi
```

(Case-sensitivity makes this safe: seismic files are `dataN.npy`/`seisN.npy`; the lowercase
`model`/`vel` patterns match only velocity files.) The existing loader already globs both layouts
(`<family>/model/*.npy` and `<family>/vel*.npy`) — **no loader change needed for folder
structure**, only a post-download verification that each family reports its expected map count.

The existing 160 GB of Vel-family `data/` (seismic) can be deleted whenever — nothing uses it.

## 2. Train/validation construction

Current mechanism (`OpenFWIDatasetConfig._split`): one seed-0 `randperm` over the concatenated
index, `val_fraction=0.1`. Two problems at 10 families:

1. **Split instability:** the permutation is a function of the *entire families list and file
   ordering* — adding a family reshuffles which maps are held out. Any future family change would
   silently leak old val maps into train.
2. **Legacy target identity:** the historical inversion target "map 6044" is only meaningful under
   the old `families=[FlatVel_A]` split.

Design:
- **Per-family split:** split each family independently with a seed derived deterministically from
  the family name (e.g. `zlib.crc32(family)`), 10% val. Stable under adding/removing families, and
  gives exactly 10% val per family (stratified for free). `_split()` keeps its signature; global
  indices remain valid for `held_out_targets`.
- **Dataset fingerprint:** log `{families, per-family file+map counts, val_fraction, split seeds}`
  into the run config and the benchmark manifest, so "trained on the canonical 470k split" is
  auditable later.
- **Legacy pin:** before anything changes, resolve map 6044's `(file, row)` provenance via
  `dataset.index[6044]` under the old config and carry it into the benchmark (§7) by provenance,
  not by index.

## 3. Diversity strategy

- **Proportional sampling** across the concatenated families (Vel 25.5% / Fault 46% / Style 28.5%)
  as the default — it is what the OpenFWI training literature does and the imbalance is mild
  (6.4–14% per family). Rebalancing (e.g. equal-per-family `WeightedRandomSampler`) would *reduce*
  Style exposure and is not obviously better; keep it as an opt-in config flag, to be pulled only
  if per-family metrics show a starved family.
- **Per-family observability (the guard):** the loader tracks a per-sample family id; each eval
  logs **per-family val loss**, and the final eval logs a **per-family energy distance** (one
  shared generated pool vs each family's held-out maps), so mode collapse or a starved family is
  visible at epoch granularity, not post-hoc. (The prior is unconditional, so *generated* samples
  carry no family label and cannot be stratified — a one-time grid of real held-out maps per
  family is logged instead as the visual reference for the sample grids.)
- **Horizontal-flip augmentation** (train split only, off for val): a left-right mirrored velocity
  model is a physically valid velocity model, and the prior is unconditional, so this doubles
  effective data for free. Vertical flip is *not* valid (velocity increases with depth).
- **EMA** stays on (already in the full configs).
- **Capacity:** diversity is bounded by model capacity — see §5; the current 7M-param DiT trained
  to val-loss plateau on 30k maps will underfit 470k.

## 4. Dataloader construction

`OpenFWIVelocityDataset` already pre-loads everything into one contiguous array shared with
workers via fork/copy-on-write. At 470k maps that is 470k × 1×70×70 × 4 B ≈ **9.2 GB resident**
(~18 GB peak during the stack) — fine on any 64 GB+ pod, so **keep the RAM-preload design**; no
mmap/streaming machinery needed. Changes:

- Add a parallel `family_ids: np.ndarray` (int8) built during load; expose `family_names`.
  `__getitem__` return stays `(x, 0)` — training remains unconditional; family ids are consumed
  by eval/metrics only.
- Add `hflip: bool` (train wrapper applies `torch.flip(x, [-1])` with p=0.5).
- Build peak-memory-friendly: pre-allocate the `(N,1,70,70)` array and fill per file instead of
  `np.stack(rows)` (halves the transient peak; trivial change).
- DataLoader: `num_workers=8`, `pin_memory=True`, `persistent_workers=True` (the 27s-epoch smoke
  suggests loader overhead is already visible at bs 256).

## 5. Model scale

Current DiT (`hidden=256, depth=6, heads=8, patch=4` @ 64×64 → 256 tokens) ≈ **7M params** — right
for 27k FlatVel_A maps, undersized for 470k maps spanning 10 structural regimes. Presets to add:

| Preset | hidden/depth/heads | ~Params | Role |
|---|---|---|---|
| `dit` (existing) | 256/6/8 | 7M | smoke + continuity |
| `dit_m` | 512/8/8 | 30M | fallback if dit_b trains poorly |
| `dit_b` | 768/12/12 | 130M | **recommended for the definitive priors** |

All patch 4, resolution 64 (keep — the inversion bridge resizes to native 70 anyway, and 256
tokens keeps attention cheap). DiT-B/4 at 256 tokens is the same token budget as DiT-B/2 at 32×32,
a very well-trodden operating point. The diffusion baseline (0003) uses the same DiT backbone via
`diffusion_prior.py`, so one preset serves all three experiments.

**Precision:** the training loop is currently fp32 with `attn_func="base"`. Add config-gated
**bf16 autocast** (and optionally `torch.compile`) to `training/loop.py` — expected 2–4× on
H100-class hardware; validate loss parity on a FlatVel_A smoke first. On H100/H200 the mfm package
supports FlashAttention v3, but SDPA at 256 tokens is likely fine.

## 6. GPU requirement + time estimates

Measured baseline (RTX PRO 4500 Blackwell 32 GB, DiT 256/6/8, fp32, FlatVel_A, 2026-06-29 runs):

| Run | Throughput |
|---|---|
| 0001 flow matching (bs 256) | ~2,300 maps/s |
| 0003 diffusion (bs 64) | ~1,900 maps/s |
| 0002 flow map, esd_teacher distill (bs 64) | ~640 maps/s (teacher forward + off-diagonal term) |

Sample budget per full run: `openfwi_full` = 45 epochs × 423k train maps ≈ **19M samples**
(297k steps @ bs 64 — mid the literature's 200k–400k band; 0003 = 30 epochs ≈ 12.7M).

**Measured dit_b calibration (2026-07-07, RTX PRO 4500, full 10-family dataset, bf16, 300
timed steps):** 297 maps/s @ bs 128, **24.3 GB peak VRAM**; **bs 256 OOMs on 32 GB** (>31 GB —
the earlier 20–30 GB estimate was optimistic). Projections from that anchor:

| Hardware | 0001 (38M samples) | 0003 (25M) | 0002 distill (~2.5–3.5×/step) | Notes |
|---|---|---|---|---|
| RTX PRO 4500 Blackwell 32 GB (current) | ~36 h (measured rate) | ~24 h | ~4–5 days | bs 128 only |
| RTX 5090 32 GB | ~18 h | ~12 h | ~2–2.5 days | bs 128 only; VRAM tight for 0002 teacher regime |
| **RTX PRO 6000 Blackwell 96 GB (recommended)** | **~14–18 h** | **~9–12 h** | **~1.5–2 days** | bs 256 fits with room for the frozen teacher |
| 1× H100 80 GB SXM | ~9–12 h | ~6–8 h | ~1–1.5 days | bs 256 fits; FA3 irrelevant at 256 tokens |

The 32 GB cards work but pay bs 128 (override `training.batch_size=128 training.lr=1.4e-4`;
same sample budget) and are tight for the 0002 teacher regime (frozen second dit_b resident).
Topology: 0001 and 0003 on two pods concurrently, then 0002 on the bigger card.
Re-calibrate on the target GPU before committing to the long runs (plan Task 4).

- **VRAM:** DiT-B @ bs 256 bf16 + AdamW + EMA ≈ 20–30 GB. 32 GB workable at bs 128–192; 80–96 GB
  comfortable (room for bs 512, and for the 0002 regime which holds frozen teacher + student + EMA
  ≈ 1.5× memory).
- **System RAM:** ≥ 64 GB (9 GB dataset + ~18 GB load peak + workers). **vCPU:** ≥ 16.
- **Storage:** trivial after §1 — ~8 GB of velocity maps total.
- **Parallelism:** 0001 and 0003 are independent → two pods concurrently. 0002 (esd_teacher)
  **depends on the finished 0001 checkpoint**. Critical path ≈ 0001 → 0002 ≈ 1.5–2 days on
  PRO 6000-class hardware.
- **Whole-program budget** incl. smoke tests, one throughput-calibration run, and slack for one
  retune per prior: **~$100–350 depending on card choice.** A real (not extrapolated) throughput
  number comes from Task 4 of the plan (1-epoch calibration on the target GPU) before committing
  to the long runs.

**Batch size / LR (decided 2026-07-06):** **bs 256, lr 2e-4** (≈ sqrt scaling from the
near-universal 1e-4 @ 64), n_epochs 90 → ~150k steps and a 38M-sample budget (2× the yaml's).
On 32 GB cards fall back to bs 128 / lr 1.4e-4 / same sample budget.

### 6.1 Checkpoint storage (wandb free plan = 5 GB total)

Checkpoints are weights-only (`save_checkpoint` stores `model.state_dict()` — no optimizer
state), so DiT-B ≈ 520 MB per fp32 `.pt`. Best + final + EMA × 3 priors ≈ 3.5–5 GB — **at or
over the free wandb cap**. This does NOT justify a smaller model; change where the bytes live
(decided 2026-07-06):

- **Primary (everything):** the RunPod network volume (`runs/.../checkpoints/`) — persistent,
  effectively unlimited, already the source of truth for 0004. All best/final/EMA files stay
  here.
- **wandb (off-RunPod copy of what matters):** set `ckpt_every_epochs: 0` for the full runs and
  upload **final EMA + final raw per prior** (6 × 520 MB ≈ 3.1 GB) plus the benchmark artifact
  (~290 MB, §7) — ~3.4 GB total, under the 5 GB free cap. Final EMA is the inference checkpoint
  (what 0004 loads); final raw is the warm-start checkpoint for any future continued training.
  "Best" is skipped: checkpoints are weights-only (no optimizer/schedule state, so every restart
  is a warm start anyway), val loss is a noisy model-selection signal for flow/diffusion priors,
  and with EMA the final ≈ best in practice. Best still exists on the volume.
- No HuggingFace mirror. Residual risk (volume mishap loses the "best" snapshots) is acceptable:
  velocity maps are kept (§9.5) and any prior is regenerable in ~a GPU-day. `docs/prior-zoo.md`
  records volume path + wandb artifact ref per prior.

## 7. Inversion benchmark set (post-training, pre-deletion)

Purpose: after checkpoints are verified, delete the bulk data and keep a **small, fixed, visually
familiar** target set that supports hypothesis-testing and side-by-side method comparison for the
inversion phase.

**Contents — `data/inversion_bench/`:**
- `manifest.json` — per target: stable id (`style_a_03`), family, source `(file, row)` provenance,
  global val index, velocity stats, structural tags (n_layers, has_fault, TV percentile), plus the
  dataset fingerprint (§2) proving val-split membership.
- `velocity/<id>.npy` — native 70×70 float32 m/s. ~2 MB total → **git-committed**.
- `previews/<id>.png` — one labeled PNG per target, fixed 1500–4500 m/s viridis scale, and a
  per-family `gallery_<family>.png` contact sheet → the "I recognise this map" workflow.
- `seismic/<id>.npy` (recommended) — the **original OpenFWI-simulated seismic**
  (5×1000×70) for each target. This is the only asset that becomes hard to get after deletion and
  it unlocks non-inverse-crime experiments (their simulator ≠ our Deepwave operator) — a caveat
  the journal already flags on every result to date. ~280 MB: volume + wandb artifact, not git.
  Requires transiently downloading only the specific `data/seis` files containing selected rows
  (~40–60 files ≈ 30–40 GB, then deleted).

**Selection: 201 targets** (decided 2026-07-06 — oversized on purpose so the seismic never has to
be re-downloaded; velocity maps are kept after deletion (§9.5), so only seismic is
hard-to-recover).
- 20 per family × 10 families, drawn **only from the canonical val split**: rank the family's val
  maps by a complexity proxy (total variation) and take percentiles {5, 25, 50, 75, 95} × 4
  independent draws — spans easy→hard within every family without hand-picking bias.
- +1: the legacy FlatVel_A map 6044 (pinned by provenance, §2) for continuity with all existing
  journal results.
- Day-to-day work can use a fixed 101-target (or smaller) subset tagged in the manifest
  (`core: true`); the rest is reserve.

**Loader:** a small `InversionBenchmark` class reading the manifest; `0004_inversion` configs gain
`target=<id>` (string id) alongside the existing index path. After deletion, `held_out_targets`'
bulk-data path is retired for benchmark use.

**Checkpoint registry:** `docs/prior-zoo.md` — one row per definitive prior: run dir, wandb
artifact ref, config summary, final per-family val metrics, sample-grid thumbnail. The 0004
configs reference priors through this registry so "which checkpoint is the canonical flow-map
prior" has exactly one answer.

## 8. Verification gates before deletion

1. Each definitive EMA checkpoint reloads **from its wandb artifact** (the off-RunPod copy, §6.1
   — not the local file) and generates a 64-sample grid without error.
2. Per-family energy distance vs held-out val within an agreed factor of the FlatVel_A-era
   baseline (0.127 vs 0.090 floor was the 0001 precedent).
3. One end-to-end inversion (flow_tilt + mfm_g on map 6044 via the new benchmark loader) matches
   journal numbers within seed noise — proves the checkpoint + benchmark pair is self-sufficient.
4. Benchmark assets (incl. seismic, ~290 MB) uploaded as a wandb artifact.

Then delete: all `data/` + `seis*` files. **Velocity maps (~8 GB) are kept** (§9.5) — cheap
insurance for retraining and for expanding the benchmark without any re-download.

## 9. Decisions (resolved 2026-07-06 unless noted)

1. **Batch size / LR:** bs 256 + lr 2e-4, n_epochs 90 (§6). ✅
2. **Model scale:** DiT-B; `dit_m` exists as fallback only. (Still open: none — proceed with
   DiT-B unless the Task 4 calibration or early loss curves argue otherwise.)
3. **0002 regime:** esd_teacher with the full-data DiT-B 0001 prior as teacher. Note the harness
   already trains the **diagonal from data** (`data_fm=True, distill_fm=False` in
   `flow_matching/train.py`) — the teacher supplies only the off-diagonal consistency target and
   the warm start, and the data-FM diagonal is *cheaper* than a distilled diagonal (no teacher
   forward for that term). Nothing to switch. From-scratch `mf` full run: deferred, optional
   ablation.
4. **Benchmark size:** 201 targets (20/family × 10 + legacy 6044), §7. ✅
5. **Velocity maps kept** after bulk deletion. ✅
